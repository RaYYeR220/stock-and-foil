# Stock & Foil — contract

The Compact contract for a private collateral registry for receivables finance, plus its
witnesses, private-state types and the simulator test suite.

Every state change is authorised by proving knowledge of a secret whose hash is on the ledger or
inside committed data — never by the caller's coin public key. A fraudulent transaction is refused
while it is being built, so it never reaches the chain; the assert messages listed below are the
product's refusal codes and the SDK maps them 1:1.

## Layout

```
src/stock-and-foil.compact      ledger, constructor, every exported circuit
src/modules/Identity.compact    domain-separated identity and tag hashes (pure)
src/modules/Invoice.compact     Invoice struct, fingerprint / ack leaf / nullifier, field packing (pure)
src/modules/Cipher.compact      ECDH sealing, Jubjub helpers, record and share keys (pure)
src/modules/BorrowingBase.compact  certificate struct and pool arithmetic (pure)
src/managed/stock-and-foil/     compiler output; the JS under contract/ and compiler/ is committed
src/witnesses.ts                witness implementations over StockAndFoilPrivateState
src/private-state.ts            private state and per-call witness inputs
test/harness.ts                 simulator harness: personas, block time, ledger reads, record opening
test/lifecycle.test.ts          happy paths for every circuit
test/refusals.test.ts           one scenario per refusal code, plus lying-witness cases
test/model.property.test.ts     fast-check model test over random lifecycles
test/disclosure.test.ts         2-of-3 threshold decryption with negative controls
```

## Build and test

```bash
npm run -w contract compile        # full build with proving keys (~2 min, needs Docker)
npm run -w contract compile:fast   # --skip-zk, seconds, for the edit/test loop
npm run -w contract test
```

`src/managed/**/keys/` and `src/managed/**/zkir/` are regenerated by `compile` and are not
committed; the generated JavaScript is, so `npm test` runs without Docker.

## Domain separators

One `snf:v1:<purpose>` domain per hash purpose, so a value derived for one role can never be
replayed as another: `operator`, `debtor`, `seller`, `financier`, `acknul`, `invoice`, `ack`,
`pledge`, `holder`, `sellerpayee`, `record`, `request`, `share`, `cert`, `borrower`.

## Refusal codes

| Circuit | Refusals |
|---|---|
| `admitDebtor`, `admitFinancier` | `NOT_OPERATOR` |
| `acknowledge` | `NOT_REGISTERED_DEBTOR`, `NOT_YOUR_INVOICE`, `ALREADY_ACKNOWLEDGED` |
| `offer` | `NOT_INVOICE_OWNER`, `NOT_ACKNOWLEDGED`, `BAD_EXPIRY`, `INVOICE_OVERDUE`, `ALREADY_SETTLED`, `ALREADY_ENCUMBERED`, `BAD_EPHEMERAL` |
| `accept` | `NOT_LICENSED`, `NO_SUCH_OFFER`, `NOT_ADDRESSEE`, `OFFER_EXPIRED` |
| `release` | `NOT_PLEDGED`, `NOT_HOLDER` |
| `certifyBorrowingBase` | `BAD_EXPIRY`, `DUPLICATE_CERTIFICATE`, `EMPTY_POOL`, `NOT_INVOICE_OWNER`, `NOT_ACKNOWLEDGED`, `INVOICE_OVERDUE`, `DUPLICATE_INVOICE`, `BELOW_FLOOR`, `ALREADY_SETTLED`, `ALREADY_ENCUMBERED`, `BAD_EPHEMERAL` |
| `payInvoice` | `NOT_YOUR_INVOICE`, `NOT_ACKNOWLEDGED`, `ALREADY_SETTLED` |
| `claimAsHolder`, `claimAsSeller` | `NOT_SETTLED`, `NOT_PAYEE`, `ALREADY_CLAIMED` |
| `requestDisclosure` | `NOT_AUDITOR`, `NO_SUCH_RECORD`, `DUPLICATE_REQUEST` |
| `approveDisclosure` | `NOT_KEYHOLDER`, `NO_SUCH_REQUEST`, `ALREADY_APPROVED`, `BAD_EPHEMERAL` |

Asserts run in the order listed, which is what the property model and the SDK rely on. In
`certifyBorrowingBase`, distinctness and the floor are proved *before* any slot is locked, so a
pool that lists the same invoice twice is refused as `DUPLICATE_INVOICE` rather than as an
encumbrance it caused itself.

## ABI notes

Deviations from the Wave 1 plan's ABI sketch, and things the SDK has to know.

**Added refusal code.** `BAD_EPHEMERAL` is not in the spec table. Sealing uses a witness-supplied
scalar `e`; if `e ≡ 0 (mod ℓ)` then `E = e·G` is the curve identity, the shared point is the
identity too and the record has no secrecy at all. Every sealing circuit asserts
`E != identityPoint()`. Add it to the SDK's `RefusalCode` union.

**Extra pure circuits.** Beyond the planned list, `pureCircuits` also exports
`ackLeafFromFingerprint`, `nullifierFromFingerprint`, `packFields`, `cipherVersion`,
`identityPoint`, `shareKeyOf`, `certIdOf`, `borrowerCommitOf`, `poolCount`, `poolTotal` and
`poolDistinct`. `operatorIdOf` and `debtorIdOf` are there as planned. The SDK needs `shareKeyOf`
and `certIdOf` in particular: they are the ledger keys of shares and certificates.

**Shares live in their own map.** The plan put `shares: Vector<3, CipherShare>` inside
`DisclosureRequest`. Compact `Map` iteration order is not insertion order, so a share is instead
stored in `shares: Map<Bytes<32>, CipherShare>` under `shareKeyOf(requestId, index)` and the
request only carries `approvals: Vector<3, Boolean>`. Look shares up by the computed key.

**Certificates carry their locked nullifiers.** Per `certify.md` a certificate is a *pool offer*:
`Certificate { borrowerCommit, lenderRef, floor, count, validUntil, nullifiers: Vector<4, Bytes<32>> }`,
with zero bytes in unused slots. Each used slot becomes an ordinary `OFFERED` pledge expiring at
`validUntil`, with its own sealed record, which the lender takes up with the normal `accept(n)`.

**Certificate slots are always four.** `certifyBorrowingBase` reads four witnesses —
`certInvoices`, `certUsed`, `certHolderTags`, `certEphemerals` — each a fixed-size vector of 4.
Unused slots **must** carry the zero invoice (`{0,0,0,0,0,0}`), the `used` flag `false`, tag `0`
and any scalar: the circuit computes their nullifier and discards it, so a real invoice parked in
an unused slot would have its nullifier computed needlessly. The SDK's `CallInputs` mirrors this
with `invoices`, `used`, `holderTags` and `ephemerals`.

**Two member-path witnesses, not one.** `debtorPathFor` and `financierPathFor` instead of a single
`memberPathFor(tree, leaf)`, because a witness cannot pick a tree at runtime. The ack tree has its
own `ackPathFor` (depth 16; member trees are depth 10). When no real path exists the witness
returns a dummy path (requested leaf, zero siblings) so the refusal comes from the circuit assert
rather than from a JavaScript exception.

**Sealed record format.** `CipherRecord { version: Uint<8>, E: JubjubPoint, ct: Vector<5, Field> }`
with `ct = [debtorId, sellerId, packFields(invoiceNo, amount, dueDate), salt, holderTag] + mask`,
`mask_j = maskOf(S, j) = transientHash([S.x, S.y, j])` and `S = e·disclosurePk`. Masks are Poseidon
images because they must be uniform over the whole field: a `degradeToTransient(persistentHash(…))`
mask is below 2^248 and would leak the high bits of the 248-bit identities and tags it pads.
Poseidon is not promised to be stable across platform upgrades, hence `version` — currently
`cipherVersion() == 1`. `CipherShare` has the same shape with `ct = [D.x, D.y] + mask` under the
auditor key. Decrypt by subtracting `maskOf` mod the field modulus.

**Time semantics.** `blockTimeLt` puts its argument in the public transcript, so a private due date
can never be passed to it. `offer` bounds block time by the public `expiry` and then privately
requires `expiry <= dueDate`; `certifyBorrowingBase` does the same with `validUntil`. Consequence:
an invoice must be due on or after the offer's expiry, and `INVOICE_OVERDUE` is what an
already-due invoice yields.

**Scalars.** Every Jubjub scalar handed to a circuit — keyholder shares, the auditor key, sealing
randomness, Lagrange coefficients — must be reduced into `[1, ℓ)` with
`ℓ = 0x0e7db4ea6533afa906673b0101343b00a6682093ccc81082d0970e5ed6f72cb7`. `ecMul` throws on a
scalar at or above `ℓ`. Opening a record with the wrong key produces plaintexts that overflow
`Uint<64>`, so `pureCircuits.nullifierOf` throws on them — wrap disclosure verification in
try/catch (see `recomputesNullifier` in the test harness).

**No public counters.** Spec §4 mentions `Counter`s for public stats. They are not implemented:
`pledges.size()`, `records.size()`, `certificates.size()`, `requests.size()` and
`acks.firstFree()` already give the same numbers without extra ledger writes per call.

**One Compact file for stateful circuits.** Spec §4 describes eight modules. Ledger state declared
inside a Compact module is private to that module and does not appear in the public ledger
projection the SDK reads, so every circuit that touches the ledger lives in
`stock-and-foil.compact`; the modules hold the pure helpers.

**Unshielded effects.** `payInvoice` calls `receiveUnshielded(settlementColor, amount)` and the
claim circuits call `sendUnshielded(...)` to a `UserAddress`, which on the TypeScript side is
`{ bytes: Uint8Array(32) }`. In the simulator they show up in
`res.context.currentQueryContext.effects` as `unshieldedInputs`, `unshieldedOutputs` and
`claimedUnshieldedSpends` (token keys carry `raw` as a hex **string**).

## Circuits and proving keys

Compiled with compactc 0.31.1 (language 0.23.0), 12 circuits, about 1 m 54 s with keys.

| Circuit | Prover key |
|---|---|
| `certifyBorrowingBase` | 42.9 MB |
| `offer` | 11.1 MB |
| `acknowledge` | 10.0 MB |
| `payInvoice` | 10.0 MB |
| `accept` | 5.2 MB |
| `claimAsSeller` | 5.2 MB |
| `approveDisclosure` | 3.1 MB |
| `requestDisclosure` | 3.1 MB |
| `admitDebtor` | 2.8 MB |
| `admitFinancier` | 2.8 MB |
| `claimAsHolder` | 2.8 MB |
| `release` | 2.8 MB |

SHA-256 (`persistentHash`) dominates key size and proof time, so every circuit computes an
invoice fingerprint at most once and derives the ack leaf and the nullifier from it. Poseidon,
`ecMul` and the depth-16 Merkle path are cheap. Budget roughly 25–30 s of proving for
`certifyBorrowingBase` on a mid-range machine and raise the proof provider's timeout accordingly.
