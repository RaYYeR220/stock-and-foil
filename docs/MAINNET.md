# Running Stock & Foil on mainnet

Mainnet contract deployment on Midnight has been permissionless since **2026-09-28**. There is
no deploy request, no Foundation review and no allowlist: the request process was formally
retired by [midnight-improvement-proposals PR #375](https://github.com/midnightntwrk/midnight-improvement-proposals/pull/375),
merged 2026-10-09.

The docs site has not caught up. [The networks
guide](https://docs.midnight.network/guides/networks-and-environments) still carries a checklist
item saying deployment authorisation must be requested, and the March 2026 "how to apply for
deployment auth" post is still live and unannotated. The fix is open but unmerged
([midnight-docs #1553](https://github.com/midnightntwrk/midnight-docs/pull/1553), opened
2026-10-14). Cite the MIP, not the docs.

What is left is purely operational, and this page is the operation.

---

## 1. Two things to acquire, in this order

### A Blockfrost project token

Midnight retired its own public endpoints: mainnet on **2026-09-30 22:00 UTC**, preprod on
**2026-10-09 22:00 UTC**. `indexer.{preprod,mainnet}.midnight.network` answers
`410 ENDPOINT_DECOMMISSIONED`, and `rpc.{preprod,mainnet}.midnight.network` still answers but is
unsupported and can stop at any time. Blockfrost is the public RPC and indexer for both.

1. Sign up at [blockfrost.io](https://blockfrost.io), create a project, select **Midnight
   Mainnet**, copy the project id. It starts with `nightmainnet`.
2. Export it. Never pass it on a command line in a shell whose history is kept:

   ```sh
   export BLOCKFROST_PROJECT_ID_MAINNET=nightmainnet...
   ```

Tokens are issued per network and are not interchangeable. The CLI checks the prefix before the
first request and refuses a preprod token on mainnet by name, because Blockfrost's own answer is
an unexplained 403. Override with `--allow-token-prefix-mismatch` if Blockfrost ever changes its
prefixes.

A missing token fails immediately with a message naming the variable, the flag and where to get
one — not twenty minutes into a wallet sync.

### DUST, which is the slow one

There is **no mainnet faucet** and no builder grant. Fees are paid in DUST, DUST is generated by
registered NIGHT, it is non-transferable, and a contract cannot hold it.

Most NIGHT lives on Cardano as cNIGHT. Register the Cardano reward address together with the
Midnight DUST public key through the **cNgD dApp**:
<https://midnight-dust-mainnet.nethermind.io/>.

Our DUST address is
`mn_dust1wdp945q3qkfsnwlgdvucltpu5w8wqf75yk7whtxdex0ffd2exrlr7j4vkp3`, and the wallet behind it
is `infra/.secrets/mainnet-wallet.json` — outside the repository, and it stays there.

The timing is the thing to plan around:

| Stage | Duration |
|---|---|
| Registration finalizes on Cardano and reaches a Midnight node | **~12 hours** |
| DUST accrues, linearly, to a cap of ~5 DUST per NIGHT | **~1 week** to the cap |

So ~200 NIGHT registered reaches roughly 1,000 DUST at the cap, and a useful fraction of that
within hours of the registration landing. Watch it arrive:

```sh
npm run -w cli balance -- --network mainnet \
  --mnemonic-file ../infra/.secrets/mainnet-wallet.json --watch 60
```

That command never waits for DUST — a wallet with none is exactly what it is for — and prints
the unshielded address, the DUST address, NIGHT, DUST, and how many NIGHT UTXOs are registered
for generation. Unregistered NIGHT generates nothing, so `utxos 0/3 registered` is the answer to
"why is the balance still zero".

## 2. Know the bill before paying it

```sh
npm run -w cli estimate -- --network mainnet \
  --mnemonic-file ../infra/.secrets/mainnet-wallet.json
```

The method, because an estimate nobody can check is worth nothing:

1. A previous run of the same deploy and the same scenario is already on chain — on preview by
   default, or `--reference preprod`. Its evidence file names every transaction it produced.
2. The indexer serves each of those transactions' **raw ledger bytes**. They are the real,
   proven, balanced transactions, with real verifier keys and real transcripts.
3. Those exact bytes are priced against the **mainnet** wallet with the ledger's own cost
   function. No scaling factor, no guessed constant, and nothing is built, proven or submitted.

It prints a per-transaction table, the total, a 25% margin (`--margin-percent` to change it) and
whether the wallet can cover it, writes the same to `cli/evidence/estimate-mainnet-*.json`, and
exits `2` when the balance is short so a script can branch.

What it does not capture, stated rather than hidden. The mainnet transactions will not be
byte-identical: different keys, addresses, salts and timestamps move a transaction's size by a
few bytes, and a contract whose state has grown costs marginally more to call. That is what the
margin is for.

And the price includes the wallet's own `additionalFeeOverhead`, 1000 SPECK per transaction, on
top of what the ledger parameters charge. Measured against the local devnet on 2026-10-16, every
transaction from 17.5 kB down to 5.7 kB priced at exactly 1001 SPECK: 1000 of overhead and 1 of
ledger fee. So on a cheap network the figure is flat and dominated by the overhead. Read the
total as an **upper bound on what a run will draw from the balance**, not as a prediction of the
ledger's own charge. On mainnet, where the parameters are not nominal, the two parts separate.

`--offline` skips the wallet entirely and reports only what the reference network charged. Run
that before the token exists.

For calibration: **preview charges 1 SPECK per transaction** — 27 SPECK for a whole deploy plus
scenario, which is 0.000000027 DUST. Preview is not a guide to mainnet pricing; it is a guide to
nothing except that the code works.

## 3. The deploy, exactly

Nothing below runs on mainnet by accident: every command that can submit refuses the network
unless `--yes-mainnet` is also present.

```sh
export BLOCKFROST_PROJECT_ID_MAINNET=nightmainnet...
export MIDNIGHT_MNEMONIC=   # leave unset; use --mnemonic-file instead

# 0. A local proof server. Every network, always: it sees witness data in the clear.
docker run -d --name midnight-proof-server -p 127.0.0.1:6300:6300 \
  midnightntwrk/proof-server:8.1.3 midnight-proof-server -v

# 1. Compile, so the proving keys match the contract being deployed.
npm run compile

# 2. The 2-of-3 disclosure key ceremony. Writes cli/.secrets/mainnet-keys.json (gitignored).
npm run -w cli ceremony -- --network mainnet

# 3. Check the bill against the balance. Exits 2 if it is short.
npm run -w cli estimate -- --network mainnet \
  --mnemonic-file ../infra/.secrets/mainnet-wallet.json

# 4. Deploy: one transaction carrying the constructor and six verifier keys, then one
#    maintenance transaction per remaining circuit.
npm run -w cli deploy -- --network mainnet \
  --mnemonic-file ../infra/.secrets/mainnet-wallet.json --yes-mainnet

# 5. The guided replay, with real proofs. Resumable: a dropped connection costs one step.
npm run -w cli scenario -- --network mainnet \
  --mnemonic-file ../infra/.secrets/mainnet-wallet.json --yes-mainnet

# 6. The judge-facing check. No wallet, no proving keys, exits non-zero on any mismatch.
npm run -w cli verify -- --network mainnet
```

`verify` still needs `BLOCKFROST_PROJECT_ID_MAINNET` in the environment, because that is how the
indexer is reached now. It needs nothing else.

### Why the deploy is staged

A Midnight block caps the bytes one transaction may write. This contract's verifier keys run to
tens of kilobytes and a deploy carrying all of them is rejected with
`1010 Transaction would exhaust the block limits`, which the node reports as a generic
submission error with no clue in it. So the deploy carries six keys and `VerifierKeyInsert`
maintenance transactions add the rest. The deployer can do that because it holds the contract's
maintenance authority, whose signing key lives in the LevelDB store under `cli/.secrets/`.

**Lose `cli/.secrets/mainnet-private-state/` and the contract can never be maintained again.**
Back it up before the deploy, not after.

### If something fails halfway

- `scenario` is resumable. Re-run the same command; completed steps are skipped. `--from <step>`
  replays from a chosen point, `--fresh` starts over.
- `deploy` is not. If it fails after the first transaction, the contract exists but is missing
  verifier keys. Re-running with `--force` deploys a *second* registry rather than repairing the
  first; the maintenance path is the repair, and it needs the private-state directory.
- A proving "timeout" whose message is `The user aborted a request.` is not a timeout. The
  midnight-js proof provider drops the proof server's own error
  ([servicedesk#243](https://github.com/midnightntwrk/servicedesk/issues/243)); read the proof
  server's logs.

## 4. Fee sponsorship on mainnet

The sponsor is the one wallet in the system that must hold DUST. Everything in
[`sponsor/README.md`](../sponsor/README.md) applies; the mainnet-specific parts are:

```sh
SPONSOR_NETWORK=mainnet \
SPONSOR_MNEMONIC_FILE=../infra/.secrets/mainnet-wallet.json \
SPONSOR_CONTRACTS=<the mainnet registry address> \
SPONSOR_BUDGET_SPECK=<a number you are willing to lose> \
SPONSOR_API_KEYS=web:<a secret> \
BLOCKFROST_PROJECT_ID_MAINNET=$BLOCKFROST_PROJECT_ID_MAINNET \
npm run -w sponsor start
```

Set the budget to a figure that can be written off, and keep API keys on for a public endpoint.
The service refuses to start without `SPONSOR_CONTRACTS` and `SPONSOR_BUDGET_SPECK`, and its
budget accounting holds under concurrency rather than only between requests.

## 5. Version pins, and why each one

The matrix is identical across preview, preprod and mainnet as of 2026-10-09.

| Component | Pinned | Why not `latest` |
|---|---|---|
| Compact toolchain | **0.31.1** | 0.33+ targets ledger 9, which is not deployed on any public network |
| `@midnight-ntwrk/compact-runtime` | **0.16.0** | npm `latest` is 0.20.0 — the ledger-9 runtime the chain cannot execute |
| `@midnight-ntwrk/platform-js` | **2.2.4** | npm `latest` is 3.0.0, same break |
| `@midnight-ntwrk/compact-js` | **2.5.1** | npm `latest` is 2.5.3; the matrix moved *back* to 2.5.1 |
| `@midnight-ntwrk/ledger-v8` | **8.1.3** | two security advisories, below |
| `@midnight-ntwrk/midnight-js` | **4.1.1** | 5.x is ledger 9 |
| `@midnight-ntwrk/wallet-sdk` | **1.2.0** | the hyphenated scope's `latest` is 1.1.0; we pin the version exactly |
| `midnightntwrk/proof-server` | **8.1.3** | ledger 8.1.3, matching the pin above |

ledger-v8 8.1.3 is not optional. It carries
[GHSA-wr7g-rr4v-jmj8](https://github.com/midnightntwrk/midnight-ledger/security/advisories/GHSA-wr7g-rr4v-jmj8)
(**critical**, 2026-10-01 — field aliases turn one entitlement into repeated contract payouts)
and [GHSA-vhp6-px6f-jv94](https://github.com/midnightntwrk/midnight-ledger/security/advisories/GHSA-vhp6-px6f-jv94)
(**high**, 2026-10-15 — a non-canonical MPT path alias lets non-NIGHT tokens inflate). The
public networks already run the fix; the pin stops us running an older ledger locally.

A plain `npm install` without these pins gives a contract runtime no public network can execute,
and the failure arrives as
[servicedesk#236](https://github.com/midnightntwrk/servicedesk/issues/236): a deploy that fails
with an error that does not name the cause. Verify after any install:

```sh
npm ls @midnight-ntwrk/compact-runtime @midnight-ntwrk/platform-js @midnight-ntwrk/ledger-v8
```

## 6. Things that will bite

- **Never cold-sync during a demo.** A fresh preprod wallet takes about 78 minutes to sync,
  almost all of it streaming ~1.4M global DUST ledger events. Mainnet is larger. Keep a wallet
  process alive, or pre-seed.
- **Saved sync state is not portable** across the Blockfrost cutover. Anything captured against
  `indexer.preprod.midnight.network` must resync from genesis.
- **Blockfrost usage limits are your plan's**, not a shared public endpoint's. A long scenario
  with per-step indexer reads is not free.
- **The ledger 8→9 fork wipes DUST state.** When it lands, every demo wallet must be
  re-registered for DUST generation before it can pay a fee. It has not landed on any public
  network as of 2026-10-16, and node 2.1.0 is still rc.4.
